# Maintenance Guide

## Deploying a New Version

The deployment process is always the same, regardless of whether it is a first deploy or an update:

```bash
bash deploy_cloudrun.sh
```

The script:
1. Builds a new Docker image from the current source via Cloud Build
2. Pushes it to Artifact Registry
3. Deploys the new image to Cloud Run (Cloud Run performs a zero-downtime rollout)
4. Re-grants the GE service account invoker permission (idempotent)
5. Prints the MCP Server URL

No downtime is expected during a redeploy — Cloud Run keeps the old revision running until the new one is healthy.

## Rotating the Azure Client Secret

Azure client secrets have a finite validity (default: 12 months when created via SETUP.md Step 1.3). When the secret expires, the server will fail to authenticate to Azure and all tool calls will return an error.

**Recommended: set a calendar reminder 2 weeks before expiry.**

### Steps

1. **Create a new secret in Azure Portal:**
   - Entra ID → App Registrations → `azure-billing-mcp-reader`
   - Certificates & Secrets → + New client secret
   - Copy the new secret value immediately

2. **Update GCP Secret Manager:**
   ```bash
   printf '%s' '<new-secret-value>' | gcloud secrets versions add Azure_secret_value \
     --project <your-gcp-project-id> \
     --data-file=-
   ```

3. **Redeploy to pick up the new secret:**
   ```bash
   bash deploy_cloudrun.sh
   ```
   Cloud Run will read the new `latest` version of the secret on startup.

4. **Delete the old Azure secret version** (optional, but recommended after verifying the new one works).

## Updating Python Dependencies

Dependencies are pinned with minimum version constraints in `requirements.txt`. To update:

```bash
# Activate local venv
source venv/bin/activate

# Check for available upgrades
pip list --outdated

# Update a specific package (example)
pip install --upgrade fastmcp

# Test locally first
python server.py

# If everything works, redeploy
bash deploy_cloudrun.sh
```

There are no lockfiles (`requirements.lock`) — Docker builds always install the latest compatible versions matching the constraints in `requirements.txt`. If you need reproducible builds, add a `requirements.lock` file generated by `pip freeze`.

## Monitoring

### Health Check

Cloud Run automatically health-checks the service. Check service status:
```bash
gcloud run services describe <service-name> --region <region> --format "value(status.conditions)"
```

### Viewing Logs

```bash
# Last 100 log lines
gcloud logging read \
  "resource.type=cloud_run_revision AND resource.labels.service_name=<service-name>" \
  --project <your-gcp-project-id> \
  --limit 100 \
  --format "table(timestamp, severity, textPayload)"
```

Or use the GCP Console: Cloud Run → `<service-name>` → Logs.

### Key Log Entries to Watch For

| Log message | Meaning |
|---|---|
| `Starting Azure Billing MCP server on http://0.0.0.0:8080/mcp` | Successful startup |
| `list_subscriptions called (caller token present: True)` | Normal tool call with authenticated GE request |
| `Failed to authenticate to Azure` | Credential problem — check secret rotation |
| `Permission denied on secret` | Cloud Run SA cannot read Secret Manager |
| `Cost Management API returned 4xx` | Azure API error — check service principal roles |

### Metrics

Cloud Run provides built-in metrics (request count, latency, error rate) in GCP Console → Cloud Run → `<service-name>` → Metrics. No additional monitoring setup is required.

## Updating the Server Code

All application logic is in `server.py`. To modify or add tools:

1. Edit `server.py` locally
2. Test locally: `python server.py`
3. Deploy: `bash deploy_cloudrun.sh`

After deploying new or renamed tools, click **Reload custom actions** in Gemini Enterprise to refresh the tool list.

## What to Back Up

The server itself is stateless. There is nothing to back up from the server itself. However, these external items should be noted:

| Item | Location | Notes |
|---|---|---|
| `AZURE_CLIENT_SECRET` | GCP Secret Manager | Back up the current secret value securely before rotating. Secret Manager keeps version history. |
| Azure role assignments | Azure Portal | Role assignments are recorded in Azure Activity Log. They do not need separate backup. |
| GE data store configuration | Gemini Enterprise Console | If the data store is deleted, the MCP Server URL, OAuth settings, and Scopes need to be re-entered. Keep a record of these values. |

---

## What NOT to Modify

| Item | Why |
|---|---|
| `server.py` Azure API versions | Changing API versions may break existing tool output format |
| `SECRET_NAME` in `deploy_cloudrun.sh` without updating Secret Manager | Secret name mismatch will cause deployment to fail |
| Azure service principal Object ID / roles | Removing roles will break tool calls silently (empty results rather than errors) |
| Gemini Enterprise redirect URIs in Entra ID | Removing or changing these breaks the OAuth login flow |

## Decommissioning

To remove the deployed service:

```bash
# Delete the Cloud Run service
gcloud run services delete <service-name> --region <region> --project <your-gcp-project-id>

# Delete the container image (optional)
gcloud artifacts docker images delete asia-south1-docker.pkg.dev/<your-gcp-project-id>/cloud-run-source-deploy/<service-name>

# Delete the secret (optional — do this after decommissioning)
gcloud secrets delete Azure_secret_value --project <your-gcp-project-id>
```

Also remove (in Azure Portal):
- The `azure-billing-mcp-reader` app registration and its role assignments
- The `gemini-enterprise-mcp` app registration
- The Gemini Enterprise data store entry
